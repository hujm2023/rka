## 七、系统架构设计（核心，15-20题，重中之重）

### 7.1 架构风格（每年必考2-4题）

#### 五大类经典架构风格

**1. 数据流风格**
- 批处理：以数据为驱动，每个组件依次处理（编译器早期）
- **管道-过滤器**：数据流式驱动，过滤器独立可并行可复用
  - 优点：复用、并行、易扩展
  - 缺点：交互式应用不适合、可能引入额外解析开销
  - 例子：Unix 管道、编译器、信号处理

**2. 调用-返回风格**
- **主程序-子程序**：单线程、过程调用层级关系
- **OO（面向对象）**：封装、继承、多态
- **层次结构**：每层只与相邻层交互，下层向上层提供服务
  - 例子：OS、TCP/IP、ISO/OSI
  - 严格 vs 宽松层次（可跨层）
- **客户/服务器(C/S)**：胖客户端、二层架构
- **三层 C/S**：表示层 + 业务逻辑层 + 数据层
- **B/S**：浏览器为统一客户端、瘦客户端

**3. 独立构件风格**
- **进程通信**：消息传递、RPC
- **事件驱动/隐式调用**：发布-订阅、组件松耦合
  - 优点：复用、易演化
  - 缺点：失去对计算的控制、数据交换困难

**4. 虚拟机风格**
- **解释器**：解释执行（脚本语言、规则引擎、JVM）
  - 4 部分：解释引擎、被解释代码、控制状态、当前状态
- **基于规则的系统**：规则库 + 推理机 + 工作内存（专家系统）

**5. 仓库风格**
- **数据库系统**：传统数据库
- **黑板系统**：知识源 + 黑板 + 控制（语音识别、AI、信号处理）
- **超文本系统**：Web

#### 现代架构风格

**6. SOA（面向服务）**
- 特征：松耦合、粗粒度、平台无关、有明确接口
- 通信：SOAP/REST，企业服务总线 ESB
- 服务标准：WSDL（描述）、UDDI（注册发现）、SOAP（通信）、BPEL（编排）

**7. 微服务**（与 SOA 对比常考）
| 维度 | SOA | 微服务 |
|------|-----|--------|
| 通信 | ESB（智能管道） | 哑管道（HTTP/MQ） |
| 数据 | 共享 | 独立数据库 |
| 服务粒度 | 粗 | 细 |
| 部署 | 集中 | 独立部署 |
| 治理 | 集中 | 去中心化 |

**8. REST**
- 资源（URI）+ 表述（JSON/XML）+ 状态转移
- 6 大约束：客户端-服务器、无状态、可缓存、统一接口、分层系统、按需代码

**9. 闭环控制（过程控制）**：传感器→控制器→执行器（嵌入式）

#### MVC / MVP / MVVM

| 模式 | 通信 | 视图与模型 |
|------|------|-----------|
| MVC | 三角通信 | View 知道 Model |
| MVP | 单向 | View 与 Model 解耦，Presenter 中介 |
| MVVM | 双向绑定 | ViewModel 双向绑定 View |

### 7.2 软件架构设计方法

**ABSD（基于体系结构的软件设计）**：
- 视角：功能、质量、商业
- 6 个步骤：架构需求 → 架构设计 → 文档化 → 复审 → 实现 → 演化
- 自顶向下、递归细化
- 用 **视角和视图** 描述架构

**架构需求分析**：
- 来源：系统质量目标、系统业务目标、系统开发人员的业务目标
- ASR（架构上有意义的需求）

**架构文档化**：
- 至少有：架构规格说明 + 软件架构测试用例与测试规格说明

### 7.3 软件架构评估（必考）

**评估方式**：
- 基于调查问卷/检查表：通用性强、主观
- 基于度量：客观、要建立度量元
- **基于场景**：核心方法（SAAM、ATAM）

**ATAM（架构权衡分析方法）— 9 步**：
1. 介绍 ATAM
2. 介绍商业目标
3. 介绍架构
4. 识别架构方法
5. 生成质量属性效用树
6. 分析架构方法
7. 集体讨论场景并定优先级
8. 再次分析架构方法
9. 展示结果

**核心概念**：
- **敏感点**：影响**单个**质量属性的架构决策
- **权衡点**：影响**多个**质量属性的架构决策（敏感点的交集）
- **风险点**：可能造成质量目标无法达成的决策
- **非风险点**：好的决策

**SAAM（最早架构评估方法）**：
- 侧重**可修改性**和**功能性**
- 步骤：开发场景 → 描述架构 → 场景分类（直接/间接） → 单个场景评估 → 场景交互 → 总体评估

**CBAM（成本效益分析）**：在 ATAM 之后做经济性评估

### 7.4 质量属性（必考2-3题）

**6 大质量属性场景**：
| 属性 | 刺激源 | 刺激 | 响应 |
|------|--------|------|------|
| 可用性 | 内部/外部 | 故障/异常 | 检测、恢复 |
| 性能 | 用户/系统 | 事件 | 响应时间、吞吐量 |
| 安全性 | 用户/攻击者 | 攻击 | 抵抗、检测、恢复 |
| 可修改性 | 开发者 | 变更请求 | 修改成本/时间 |
| 可测试性 | 测试人员 | 测试 | 覆盖度 |
| 易用性 | 用户 | 操作 | 学习成本、效率 |

**6 部分质量属性场景**：刺激源、刺激、制品、环境、响应、响应度量

**质量属性战术**（每年必考辨析）：

**可用性战术**：
- 错误检测：心跳(ping/echo)、异常、Ping/echo
- 错误恢复：表决、主动冗余（热备）、被动冗余（温备）、备件、回滚、降级
- 错误预防：从服务中删除、事务、进程监视器

**性能战术**：
- 资源需求：减少计算开销、降低事件率、限制执行时间
- 资源管理：引入并发、维持多个副本、增加可用资源
- 资源仲裁：调度策略（FIFO、固定优先级、动态优先级、SJF）

**安全性战术**：
- 抵抗攻击：用户认证/授权、限制暴露、维护数据机密完整性
- 检测攻击：入侵检测系统
- 从攻击中恢复：恢复=可用性战术；识别=审计追踪

**可修改性战术**：
- 局部化变更：高内聚、抽象通用服务、预期期望变更
- 防止连锁反应：信息隐藏、维持现有接口、限制通信路径、使用中介
- 推迟绑定时间：运行时注册、配置文件、多态、组件替换

**可测试性战术**：内置监视器、记录/回放、接口实现分离

**易用性战术**：分离用户接口（MVC）、支持用户主动（取消、撤销）

### 7.6 DSSA（特定领域软件架构）

- 三大支撑：领域分析、领域设计、领域实现
- 三个层次：领域开发、领域专家咨询、应用开发

**DSSA 角色**：
- 领域分析师：组织 DSSA，控制开发过程
- 领域设计师：控制开发过程，根据领域知识做设计
- 领域实现者：根据设计实现可复用构件
- 应用工程师：使用 DSSA 构建应用

### 7.7 构件与中间件

**构件 = 对象+规范+约束**，可独立部署、第三方组装

**构件标准**：
- **CORBA**（OMG）：分布式对象架构
- **EJB**（Sun/Oracle）：Java 企业组件
- **DCOM/COM+**（Microsoft）：Windows 构件
- **.NET**（Microsoft）：跨语言

**CORBA 三个层次**：
1. 应用层：用户应用程序
2. 公共设施：水平/垂直公共设施
3. 对象服务：基础对象服务（命名、事件、生命周期等）

**中间件分类**：
| 类型 | 代表 |
|------|------|
| 数据库访问 | ODBC、JDBC |
| 远程过程调用 | RPC、gRPC |
| 面向消息 MOM | RabbitMQ、Kafka、ActiveMQ |
| 分布式对象 | CORBA、RMI、DCOM |
| 事务处理 | Tuxedo、JTA |
